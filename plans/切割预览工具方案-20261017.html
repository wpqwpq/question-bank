切割预览工具 · 技术方案

questionBank / plans / 2026-10-17 · 单进程 · 10 万题量级 · Windows 本地
一句话结论：做成 一个 Python 文件 + 一个内嵌 HTML，双击启动、自动开浏览器、不装 npm、不跑构建。 真正的难点不是"显示一张图"，而是在 32 万个文件里让首屏 1 秒出来——所以核心是先把元数据抽成 SQLite 索引， 运行时只查库、只读图，绝不扫盘。

01先说清"不分前后端"这件事

技术上没法真的没有前端——要显示就得有 HTML/JS。可以做到的是没有"前端工程"：

维度打标台现在的做法本工具的做法
进程uvicorn 单进程 + 前端 dev server单进程，标准库 http.server
前端构建Vite + React + TS，dist/ 打包无构建，一个 HTML 字符串嵌在 .py 里
依赖fastapi / uvicorn / react 全家桶pymupdf + Pillow（本机已有）
启动start.cmd + 两个终端双击 preview.cmd → 自动开浏览器
部署本地 + 服务器两套只有本地一份，不上服务器
边界声明：这个工具只读。不写 data/、不碰 confirmed.json、不改 cut.json。 缓存全部落在工具自己的 .cache/ 里。所以随便跑、随时按 Ctrl+C，不会污染题库，也不会和打标台（8642）撞车—— 端口用 8645。

  1. 不能在运行时扫盘。"打开工具 → 扫一遍 → 显示"这套在 10 万题下要 40 秒以上。必须持久化索引，启动只做卷级 stat 增量（3 秒）。

03现有数据有个质检盲区，工具的价值要落在这

如果工具只是"按 confidence 从低到高排一下"，那它没用。因为：

cut.json 自带信号7396 题中含义
status = auto7298 (98.7%)只有 98 条 review，0 条 failed
confidence = 1.06732 (91.0%)脚本自评满分——但脚本本身可能有系统偏差
confidence < 0.9142 (1.9%)筛出来也就 142 条，撑不起一个工具
review_notes 非空17 (0.2%)几乎等于没有
跨页拼接题（regions > 1）2188 (29.6%)最大风险源：接近三成题是两页拼起来的，但 confidence 照样给 1.0
关键判断：置信度几乎全是 1.0，说明它是"锚点匹配成功"的日志，不是"切割正确"的度量。 一个跨页题把下一页的页眉粘进来、或者题图底部被切掉半行字，confidence 一样是 1.0。

所以本工具必须做内容级复算——用 PDF 文字层和像素，独立判断每一刀切得对不对。这才是"预览切割效果"的真实含义。

好消息：三局（edexcel / aqa / cie）的 cut.json 结构已经完全统一（anchors + confidence + status 都有）， layout.json 里的 src_map.segs[].img 还能精确定位拼接缝在题图上的像素位置——这两点是复算可行的前提。

04三条路线，为什么选中间那条

路线首屏依赖一句话裁决
A. 纯静态 HTML
File System Access API		 2–5 min0（Edge 原生） 否决 目录授权后要用 dirHandle.entries() 遍历 32 万文件，浏览器 API 比 os.walk 慢 5–10 倍；而且没法服务端渲染 PDF 页、没法预生成缩略图。卡死在第一步。
B. 单进程 Python
推荐		 3 spymupdf + Pillow Python 天然处理 Windows 文件系统；SQLite 做索引；标准库 http.server 起服务；前端一个字符串。零构建、零 npm、双击即用。
C. 桌面壳
pywebview / Tauri		 3 s+ GUI 运行时 备选 好处是像个原生 App（独立窗口、无标签页）。但调试要开独立 devtools、打包体积翻倍。v1 不做，将来想要"图标双击"再套壳，代码不用改。
D. 预生成静态站 0.1 s需先跑生成器 否决 运行时确实最轻，但数据一改就要全量重生成（45 分钟缩略图），迭代时没法用。

选 B 的理由可以概括成一句：10 万题下，唯一不能省的是"索引"和"缩略图缓存"，而这两件事都需要一个常驻进程来做。 只要有了常驻进程，再让它顺手把 HTML 也发出去，成本几乎为零。

05架构

06索引模型（这是整件事的地基）

三张表就够。关键是把 10 万个 layout.json 里的必要字段抽出来存成行，让"筛选 / 排序 / 统计"全部变成 SQL，不再碰文件系统。

-- 卷：4740 行
papers(
  id            TEXT PRIMARY KEY,  -- edexcel/a-level/physics/2020-jan-wph11
  board, qual, subject TEXT,
  year INT, session TEXT, paper_code TEXT,
  page_count INT, dpi INT,
  n_questions INT, n_flags INT, flag_max INT,
  src_sha TEXT,                    -- 和 cut.json 里的 source.sha256 对齐
  dir_mtime_ns INTEGER,            -- 增量扫描的判据（配合 size）
  scanned_at INTEGER
);

-- 题：10 万行
questions(
  qid           TEXT PRIMARY KEY,  -- ...2020-jan-wph11-q01
  paper_id TEXT, number TEXT, idx INT,
  total_marks INT, qtype TEXT, section TEXT,
  status TEXT, confidence REAL,
  regions_json TEXT,               -- [[page,x0,y0,x1,y1], ...]
  anchors_json TEXT, subs_json TEXT, opts_json TEXT,
  img_rel TEXT, layout_rel TEXT,
  px_w INT, px_h INT,              -- 切片像素尺寸（判定高矮异常）
  n_segs INT,                      -- >1 即跨页
  flags TEXT,                      -- "A2,B1,C1"
  severity INT                     -- 0–100，排序用
);

-- 已看标记：和打标台的 confirmed.json 完全隔离
reviewed(qid TEXT PRIMARY KEY, ts INTEGER, note TEXT);

-- 索引
CREATE INDEX ix_q_paper  ON questions(paper_id, idx);
CREATE INDEX ix_q_sev    ON questions(severity DESC);
CREATE INDEX ix_q_flags  ON questions(flags);

为什么不直接用一个大 JSON？10 万条 × 1.5 KB ≈ 150 MB，每次启动都要全量 load 进内存，再在 JS 里筛——首屏直接 2 秒起。 SQLite 只读需要的 200 行，进程内存稳在 400 MB 以内。

07三个视图，各自解决一个具体问题

视图看到什么回答什么问题技术要点
页视图
叠框		 PDF 原页 110 dpi（可切 200），全部题框用 SVG 叠加，每题一色、左上角标题号；当前题高亮，其余半透明 40%。 "这刀切在哪儿？"
框有没有压到隔壁题、有没有吃页眉、跨页题第一段是不是切在句中、题框之间的空隙对不对。		 框坐标是 pt，页图是 px，换算 px = pt × dpi / 72；page_size 从 cut.json 拿，不用问 PDF。
题流
主力		 竖向卡片，一屏 3–8 题，按 ↑↓ / J K 走。卡片上叠：切割框轮廓、拼接缝虚线、异常徽章、分值/题型。 "这一刀切出来的东西对不对？"
这才是通检的主界面——看图本身，不是看坐标。		 题图按需 <img> 加载 + 预取前后 20 张缩略，翻页无白屏。
网格
扫异常		 260 px 缩略图墙，一屏 60–100 个，默认按 severity 降序，异常题加红/黄描边。 "10 万题里哪 200 个要先看？"
人不可能全看，网格负责把最可疑的挑出来。		 缩略图服务端生成（7 KB），虚列表只渲染可见 ±10 个。

两个细节值得单独说

① 拼接缝可视化。layout.json 的 src_map.segs[].img 给出每段在题图内的像素区间， 所以跨页题（29.6%！）可以在题图上精确画出那条 1395 px 的接缝虚线。 接缝上下是否有多余空白、内容是否错位、页眉是不是被粘进来——一眼能看见。 这是本工具比"看原图"强的地方。
② 题图 ↔ 原页双向映射。鼠标点在题图任意位置，用 src_map 反算出"这是第 6 页 y=669 pt"， 页视图立刻跳过去并高亮同一点。反之悬停原页上的框，题流滚到对应题。 查"这一半是从哪来的"不用再人肉比对两幅图。

08自动质检：工具的核心价值

分三层跑，成本从 0 到高，只让候选题往下走。目标：用 200 条待查队列覆盖大部分真问题。

L1 结构层 · 纯数据，全量 10 万题 ≈ 0 成本

码检测判据误报严重度
A1题框越出页边bbox 超出 page_size，或距页边 < 12 pt低高
A2相邻题叠框本题与下一题 bbox 垂直重叠 > 2 pt低高
A3切片高矮异常px_h < 80 或 > 2600（实测 max 6877，跨三页）低中
A4题号断裂卷内题号序列缺号 / 重号 / 非递增无高
A5分分之和不符Σtotal_marks ≠ paper.md 卷总分中中
A6跨页无分隔n_segs > 1 且 sep_h = 0低中
A7小问锚点缺失subquestions 有 n 个，anchors 覆盖少于 n 个中中
A8MCQ 热区不全qtype = mcq 但 option_hotzones ≠ 4低中

L2 文本层 · 用 PDF 文字层独立验算，10 万题 ≈ 4 min（一次性入库）

码检测判据误报严重度
B1框内混入他题题号题框内出现匹配 ^\d{1,2}\s 的行，且编号 ≠ 本题低高
B2框外漏切本题文字框下缘 12 pt 内有文字行，字号/缩进与本题一致中高
B3框吃到页眉页脚框内 y < 40 pt 或 y > page_h − 30 pt 存在文字低中
B4起始锚点不在框内anchors.start 的 bbox 未被 regions 包含无高
为什么 L2 是关键：L1 只能发现"几何上不对劲"，L2 能发现"几何正常但语义错了"—— 比如框整体下移 30 pt，高度还是对的，A1–A8 全过，但 B1 立刻报"框内出现下一题的题号 7"。
成本：每卷开 PDF 一次 15 ms + 取文字层约 50 ms，4740 卷 ≈ 5 分钟，一次性写入索引。

L3 像素层 · 解码昂贵，只跑候选（L1/L2 命中 + 10% 抽样）

码检测判据误报严重度
C1图被切断题框边界 ±4 px 内存在连续 > 30 px 的非白像素群中高
C2切空非白像素占比 < 0.3%低中
C3拼接缝错位接缝上下 40 px 的行投影峰谷不连续中中
C4与相邻题重复相邻两题图 perceptual hash 距离 < 5低高

排序公式（只是个起点，跑起来再调）：severity = Σ(规则权重) × (1 + 是否跨页) × (1 + 是否 review 状态)， 同一卷内累加一点卷级风险，让问题卷整体往前排。

09Windows 文件系统的九个坑

坑现实表现对策
260 字符路径上限现在最长 74 字符，余量很大；但换个更深的根目录（比如 OneDrive 同步盘）会爆所有路径读写统一走 \\?\ 前缀包装，从第一天就上，别等到出错
Defender 实时扫描首个读 10 万个小文件时，每个都要过一遍扫描 → 冷启动慢 3–10 倍建议把 data\ 和工具缓存目录加排除项（给一条 PowerShell 命令，问他愿不愿意加）
文件被占用切割脚本 / 打标台正在读 source.pdf，这边打开失败一律 open(..., 'rb')；失败重试 3 次 × 80 ms；仍失败则该卷标记 locked 跳过，不中断整库扫描
大小写不敏感Q01.webp 与 q01.webp 在同一目录会冲突；换个系统就炸入库时检测同目录重复（忽略大小写），冲突直接报 A4 类问题
路径分隔符混杂Python 给 \，JSON 里是 /，前端拼 URL 时容易双斜杠库里一律存 / 相对路径，Path() 只在真正读盘那一刻用
中文 / Unicode 文件名某些老工具按 ANSI 代码页读会乱码全程 UTF-8；HTML 显式 <meta charset>；不调用任何 cmd /c dir 之类的外部命令
mtime 精度FAT 是 2 秒精度；跨盘复制会改 mtime增量判据用 (size, mtime_ns) 双键，任一变化就重扫该卷
硬链接备份backup.sh 用硬链接快照，缓存文件放 data/ 下会被算进去缓存目录放工具目录 .cache/，不进 data/
枚举顺序不稳定os.walk 顺序不保证，索引主键若用序号会导致 id 漂移主键一律用路径派生的稳定字符串，序号只做展示排序

13明确不做的事

  • 不做打标。标签、难度、primary_tag 全归打标台，这个工具一个都不碰。
  • 不做小问级切割预览（v1）。子图是云端切的，本地没有产物；等云端那套稳定了再考虑拉回来预览。
  • 不做多人协作 / 权限 / 登录。本地 127.0.0.1，只有你自己用。
  • 不做小屏适配。沿用 1080p 及以上好用的原则，固定左栏 240 + 右栏 300。
  • 不上服务器。云端只有 data/ 的一份拷贝，预览工具留在本机。
  • 不做 PDF 全文搜索。要搜题干时用现成的 grep 或 md 文件，不在这里造。
