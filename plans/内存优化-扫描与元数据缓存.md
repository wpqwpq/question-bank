# 内存优化方案：① 目录扫描 ② 元数据缓存

> 2026-10-28。基于线上实测（`/tmp/bench_scan.py`、`/tmp/bench_scan2.py`、`/tmp/mem_probe.py`）。
> 结论先说：**① 治的是延迟，不是内存；② 治的是未来，不是现在。**

---

## 零、先修正一条判断

上一轮我把 ① 说成"内存 churn 主因、收益最大"。实测推翻了：

| 版本（线上 200 次强制重扫） | 单次耗时 | RSS 增量 |
|---|---|---|
| 现状（每次 scandir + 新建 Paper） | 160–179 ms | +6.6～6.8 MB，**然后饱和归零** |
| 复用 Paper 实例（仍 scandir） | 143 ms | +0.0 MB |
| **复用实例 + 跳过 scandir** | **78.6 ms** | +0.1 MB |

- Paper 对象 churn **不是内存大头**——分配器在 +6.8MB 后就复用完了，第三轮跑增量为 0。
- 大头是 `os.scandir()` 遍历全库 **8 万个目录项**，占了 167ms 里的绝大部分。
- 所以 ① 的真实价值是**把每 5 秒一次的 167ms 抖动抹掉**，打标时那一瞬间的卡顿会消失；对 RSS 基本无感。

## ① 目录扫描：两级扫描 + 复用 Paper 实例

### 现在怎么做的

`store.py`：

| 位置 | 内容 |
|---|---|
| `_SCAN_TTL = 5.0`（约 522 行） | 扫描结果缓存 5 秒 |
| `_scan_papers()`（约 561 行） | 逐级 iterdir/stat + **每个 session 目录 scandir** + 每次 `Paper(...)` 新建 |
| `iter_papers()`（约 872 行） | TTL 过期就重扫，`_papers_by_id` 整表替换 |

调用链决定了它的频率：

```
GET /api/questions/{qid}
  └─ store.find_question()
       └─ find_paper(paper_id)
            └─ iter_papers()        ← 每个详情/打标请求都走这里
```

`iter_papers()` 本身有 TTL 保护，但只要距上次扫描超过 5 秒，**下一个请求就要替全库扛一次 167ms 的全量扫描**。老师连续打标时，这个代价每 5 秒出现一次。

### 核心洞察

`_scan_papers()` 里唯一昂贵的一步是：

```python
if any(f.name.startswith("q") and f.name.endswith(".md")
       for f in os.scandir(session)):
```

它要读 **4053 个目录、共 80,377 个目录项**，只为回答"这个卷里有没有 q*.md"。

但这个结论**只在目录内容增删时才变**，而目录内容增删**必然改目录 mtime**。所以目录 mtime 没变，就没必要再读一遍目录。

### 改法

`_scan_papers` 增加一个 `prev` 参数，按 id 复用：

```python
def _scan_papers(prev: dict[str, Paper] | None = None
                 ) -> tuple[list[Paper], tuple[tuple[str, int], ...]]:
    papers: list[Paper] = []
    stamp: list[tuple[str, int]] = []
    prev = prev or {}
    ...                                    # 前面的逐级遍历不变
                for session in sorted(p for p in subject.iterdir() if p.is_dir()):
                    try:
                        st = session.stat()
                    except OSError:
                        continue
                    stamp.append((f"{skey}/{session.name}", st.st_mtime_ns))

                    pid = paper_id_for(session, board.name,
                                       qualification.name, subject.name)
                    old = prev.get(pid)
                    # 目录 mtime 没变 = 卷里没增删文件 → 沿用旧实例，
                    # 连 scandir 一起跳过；_qfiles / _sub_files 的 glob 结果也保住了
                    if old is not None and old.dir_mtime == st.st_mtime_ns:
                        papers.append(old)
                        continue
                    if any(f.name.startswith("q") and f.name.endswith(".md")
                           for f in os.scandir(session)):
                        papers.append(Paper(session, board.name, qualification.name,
                                            subject.name, dir_mtime=st.st_mtime_ns))
    return papers, tuple(stamp)
```

`iter_papers()` 里把旧表传进去：

```python
    papers, stamp = _scan_papers(_papers_by_id)      # ← 原为 _scan_papers()
```

### 为什么安全

| 场景 | 目录 mtime | 行为 | 正确性 |
|---|---|---|---|
| 上传新卷 | 变（subject 或 session 目录） | 全扫，新卷出现 | ✅ 与今天一致 |
| 删题 / 删卷 | 变 | 全扫，`_qfiles` 重新 glob | ✅ |
| 重切题包（增删 qNN-a.md 子题） | 变 | 全扫 | ✅ |
| **只改 q01.md 内容**（前端保存标签） | **不变** | 复用旧 Paper，`_qfiles` 仍是同一批路径 | ✅ meta 走 mtime/size 校验，照常失效 |
| `touch` 目录但内容没动 | 变 | 多扫一次 | ✅ 无害 |

关键在于：复用只影响**路径列表**，而路径列表只在目录项变化时才需要更新；文件内容变化由 `read_meta` 的 `(mtime_ns, size)` 校验兜住。

### 边界情况

- `_paper_from_index()` 造出来的实例 `dir_mtime=None`，永远不满足 mtime 相等 → 走全扫，下次扫描换成带 `dir_mtime` 的实例。这批数量极少，且下次扫描自愈。
- 进程刚启动时 `_papers_by_id` 为空 → 全部走原路径，零行为变化。

### 收益

- 单次扫描 167 ms → **78.6 ms（-53%）**，实测。
- 还能继续压：`stamp`（4053 个 tuple）和 `_papers_by_id`（4053 项 dict）现在每次仍重建。若比对后完全无变化，直接 `return _papers`，可再降到 **30–40 ms**。这一步收益递减，建议先做上面的，观察一两天再说。
- **TTL 不用改**。跳掉 scandir 之后 78ms 可接受，保留 5 秒的"上传即见"体验比省那点开销重要。

### 要改的文件

只动 `store.py` 两个函数（`_scan_papers`、`iter_papers`）。不碰数据、不碰索引、不触发 `rebuild`。回滚 = 换回文件 + restart。

## ② 元数据缓存：加 LRU 上限

### 现在怎么做的

`store.py` 约 511 行：

```python
_meta_cache: dict[str, tuple[int, int, dict[str, Any]]] = {}
```

- **无上限、无淘汰**，键是文件绝对路径
- 上界 = 全库 md 数：主文件 53,439 + 子题 22,992 = **76,431 条**
- 实测全量塞满：RSS 30.4 MB → **279.1 MB**，即缓存本身 **≈ 250 MB**
- 当前实际约 2 万条（atime 统计启动后读过 19,934 个 md）≈ **66 MB**

### 改法

```python
from collections import OrderedDict

_META_CACHE_MAX = int(os.environ.get("QBANK_META_CACHE_MAX") or 30000)
_meta_cache: "OrderedDict[str, tuple[int, int, dict[str, Any]]]" = OrderedDict()


def read_meta(path: Path) -> dict[str, Any]:
    key = str(path)
    try:
        st = path.stat()
    except OSError:
        with _lock:
            _meta_cache.pop(key, None)
        return {}
    with _lock:
        hit = _meta_cache.get(key)
        if hit is not None and hit[0] == st.st_mtime_ns and hit[1] == st.st_size:
            _meta_cache.move_to_end(key)        # 命中即提权
            return hit[2]
    meta, _ = parse_front_matter(path.read_text(encoding="utf-8"))
    with _lock:
        _meta_cache[key] = (st.st_mtime_ns, st.st_size, meta)
        _meta_cache.move_to_end(key)
        while len(_meta_cache) > _META_CACHE_MAX:
            _meta_cache.popitem(last=False)     # 淘汰最久未用的
    return meta
```

顺手把"取锁两次"合并了（原来 `get` 在锁内、`if` 判断在锁外）。

### 安全性（已核对）

- `_meta_cache` 全项目只在 `store.py` 出现 5 处（511/531/534/539/546），封装干净。
- **全库没有任何地方就地修改 `read_meta()` 返回的 dict**——已 grep `read_meta(...)[`、`meta["x"] =`、`meta.update(` 全部无命中。所以淘汰、复用都不会出现"缓存对象被外部改脏"。
- `_drop_meta()` 用的 `pop(key, None)` 对 `OrderedDict` 同样有效，不用改。
- 淘汰后下次重新解析一次 ≈ 0.2 ms，对请求无感。

### 收益：**对当前几乎为零，这点必须说清楚**

当前只用了 2 万条，上限设 3 万 → **根本不会触发淘汰**。它是"防止未来某天涨到 250MB"的保险，不是治现在 725MB 的药。

想让内存立刻降下来，上限得设到 **8000–12000 条**（≈20–26 MB），代价是热数据被挤出去重解析。以当前访问分布（昨天 6.9 万请求但只覆盖 2 万个文件），2 万条基本就是活跃工作集，设 8000 会明显降低命中率。

**建议：上限设 30000（防未来），不要指望它降当前内存。**

## 三、那 725MB 到底怎么办

如实说：单线程复刻负载只有 135MB 左右（基线 62.6 + meta 66 + churn 7），线上 725MB 差 **约 590MB**，我还没定位到。

目前最像的解释是**glibc 多 arena 碎片**：

- `rw-p anon` 有 **52 个段**分摊 725MB，没有单一巨块——这是多 arena 的特征，不是单个大对象。
- 单线程脚本只绑定 1 个 arena，所以压测怎么跑都到不了 700MB。
- 线上有 anyio 线程池（`Threads=7`），每个线程第一次 malloc 会绑定一个新 arena；glibc 默认每核 8 个，4 核最多 32 个 arena，每个都能按需涨到几十 MB 且**不归还操作系统**。

验证成本极低，一行环境变量：

```ini
# /etc/systemd/system/qbank.service 的 [Service] 段
Environment="MALLOC_ARENA_MAX=2"
```

`daemon-reload` + `restart` 之后观察 RSS。如果掉到 250–300MB，就坐实了。
副作用：多线程分配会争用同一个锁，理论上略微降低吞吐；但这种 IO 型服务基本感觉不到。

**这条比 ①② 都更可能一次性解决问题**，而且零代码风险、随时回滚。

## 四、建议的落地顺序

| 顺序 | 动作 | 风险 | 预期 |
|---|---|---|---|
| 1 | `MALLOC_ARENA_MAX=2` + 重启 | 极低（一行 env） | 若坐实，725MB → 250–300MB |
| 2 | ① 两级扫描（跳过 scandir） | 低（只动 store.py 两个函数） | 详情请求不再每 5 秒抖 167ms |
| 3 | ② LRU 上限 30000 | 低 | 防未来涨到 250MB |
| 4 | 可选：`stamp`/`_papers_by_id` 无变化时整表复用 | 低 | 78ms → 30–40ms |

1 和 2 可以一次重启一起上；3 可以顺带带上。4 等观察后再定。

全部只动 `store.py` + 一个 systemd 环境变量，**不碰数据、不碰 `index.db`、不触发 `rebuild`**。回滚：文件换回 + 去掉 env + restart。
