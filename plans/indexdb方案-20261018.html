先看这一句 你现在这套系统把「每个题的信息」全存在一个个 md 文件里，每次要用就现场翻文件。题少的时候这是最省事的做法，题多的时候就是灾难。index.db 的做法是：抄一本目录册出来，查路用目录册，正文还回原文件找。原文件一个字不改，目录册随时可扔可重抄。

1. 先用一个比喻把话说清

把题库想成一个图书馆。

  • md 文件 = 书架上的书。每本书第一页写着「书名、年份、科目、分类标签」。这些是唯一真货，改一个字都得改这儿。
  • 现在的程序 = 一个没有目录的图书管理员。你想知道「2019 年有哪些物理卷、各自打完标签没」，他就得一排一排走、一本一本翻开第一页看。走完 9176 本要 13 秒。走完 10 万本要 143 秒。
  • index.db = 前台那个卡片盒。每本书抄一张卡片：书名、年份、科目、标签打完没、书在哪个架子。查「2019 物理」时翻卡片盒，0.4 毫秒出结果。

关键在于：卡片盒不是书。卡片丢了、抄错了、撕了重抄，书一本都不会少。这就是这套方案的核心原则——index.db 永远是「派生品」，删掉就能重新长出来。

一个必须先讲清的名词：SQLite 你听到「数据库」可能会想到 MySQL、PostgreSQL 那种要装服务、要开端口、要连账号的东西。SQLite 不是。整个数据库就是一个磁盘文件（index.db），Python 标准库自带，import sqlite3 就能用，不用装任何软件、不用开任何端口。你可以把它理解成「一个能用 SQL 语句查询的 Excel 文件」。

2. 现在这套系统到底怎么跑的

我把代码里的真实链路抽出来了（cloud/workbench/backend/）。一次打开列表页，后端做的事是：

浏览器 GET /api/papers │ ├─ ① _scan_papers() 走一遍 data/ 目录树，记下每个目录的修改时间， │ 得到 486 个「卷」对象 ← 实测 0.10s │ ├─ ② 对每一卷 Paper.summary() 读这卷第一题 q01.md 的第一页 │ 拿 paper_code / year / session │ ├─ ③ 对每一卷 Paper.questions() 遍历这卷每个 qNN.md，读第一页 │ （read_meta 有缓存：文件没变就不用重读） │ 算每题状态 done / none │ └─ ④ 再读 confirmed.json、flagged.json 数出「已确认几题」「标了几题」

其中 read_meta() 就是「翻开书看第一页」：读文件 → 用 YAML 解析第一页那段 --- ... --- → 过一遍 JSON Schema 校验 → 存进内存字典 _meta_cache，键是文件的「最后修改时间 + 大小」。文件没动过，下次直接拿内存里的。

另外还有一份 _qid_index：题号 → 这道题在哪个文件。开机时全量建一遍（store.warm()）。

这套设计有一个隐藏的脆弱点 缓存判断「文件变没变」靠的是文件的最后修改时间（mtime）。问题是：rsync、备份恢复、git checkout 都会把整库文件的修改时间刷成「现在」。也就是说，只要你做一次恢复或同步，10 万个文件的缓存全部作废，下一次有人点开列表页，后端就要现场重新解析 10 万遍——143 秒的白屏。这不是假设，10-17 的方案评估里「列表页会到十几秒」就是这么来的。

下面每个数字都是我在你本机用当前 9176 个题文件跑出来的，不是拍脑袋估的。

坎现在（9176 题）10 万题为什么会这样
① 冷启动
开机 / 缓存全失效时		 13.07s（纯解析实测）
≈ 1.42ms/题		 143s 每道题都要读盘 + 解析 YAML。YAML 解析器慢，这是主要成本，不是读盘。
② 常驻内存 约 26MB（2830 字节/题） 270MB 解析出来的字典全留在内存里当缓存。加上题号索引、确认名单，总量 350–400MB。
③ 每次请求重算 列表页几十 ms 1.5–3s /api/papers 每次请求都要走目录、逐卷算状态，不算完不返回。
④ 确认名单

注意 ② 最要命。服务器 3.7G 内存、qbank.service 设了 MemoryMax 1200M。10 万题光缓存就吃掉 270MB，再加 FastAPI 自身、图片流、并发请求的临时内存——一旦超限，systemd 直接把服务杀掉，表现是「打标台突然打不开，过一会儿又好了」。这种故障最难查。

所以真正卡住的不是「查得慢」 是「开机慢」+「内存贵」。这两点恰好是 SQLite 最擅长的：它把「全部装进内存」换成「存在磁盘上，用到哪页读哪页」。内存占用从 270MB 掉到几十 MB，冷启动从 143 秒掉到 30 秒左右。

4. index.db 里到底存什么

原则：只抄「查询时要用到的字段」，正文、题图、坐标一律不抄。因为正文和坐标只在你打开某一题时才需要，直接读那个 md 就行，快得很（几毫秒）。

实测我今天真的把现有 9176 题灌了一遍，两张表，整个文件 7.4MB。表结构如下：

-- 表一：卷（486 行 → 10 万题时约 1430 行）
CREATE TABLE papers (
  paper_id        TEXT PRIMARY KEY,   -- 目录名，如 2019-jan-ph01
  board           TEXT,              -- aqa / cie / edexcel
  qualification   TEXT,              -- a-level
  subject         TEXT,              -- physics / chemistry …（学科隔离靠它）
  unit            TEXT,              -- U1–U4，从卷号推出来
  paper_code      TEXT,
  year            INTEGER,
  session         TEXT,
  question_count  INTEGER,           -- 这卷几题
  annotated_count INTEGER,           -- 打完标签几题（由 questions 表聚合得出）
  source          TEXT
);

-- 表二：题（9176 行 → 10 万行）
CREATE TABLE questions (
  qid             TEXT PRIMARY KEY,  -- 那道题的 id，全库唯一
  paper_id        TEXT,              -- 属于哪卷
  parent_qid      TEXT,              -- 是某题的小问就填父题 id
  question_number TEXT,
  sub_label       TEXT,              -- 小问标号 1/2/3
  total_marks     INTEGER,
  question_type   TEXT,
  split           INTEGER,           -- 是否被切分过
  status          TEXT,              -- done / none（列表页最常用的筛选项）
  difficulty      TEXT,
  primary_tag     TEXT,
  tags            TEXT,              -- JSON 数组文本，如 ["u1-neutrino"]
  image           TEXT,              -- 相对路径，找图用
  file_name       TEXT               -- 要读原文时去哪个文件
);

CREATE INDEX idx_q_paper  ON questions(paper_id);
CREATE INDEX idx_q_status ON questions(status);

实测出来的查询速度（9176 题的真实库）

查询耗时说明
列出全部卷（列表页主体）0.375 ms只扫 papers 表 486 行，完全不碰 questions 表
某卷的全部题0.044 ms走 paper_id 索引
按题号定位一个文件0.0045 ms主键索引，比现在快 1000 倍量级
全库按卷统计「打完了几题」0.24 ms10 万题约 2.6ms，仍然可忽略

对照：现在每请求光是走目录就要 0.1 秒（10 万题 1 秒），解析 YAML 更是 13 秒。差了 3–4 个数量级。

顺手消掉一处冗余 现在 paper_code / year / session / subject 这些「卷级」信息，在每一道题的 md 里都重复写了一遍——9176 道题里重复了同样的内容。index.db 把它们提到 papers 表，一份就够了。这是白捡的好处，不算额外改造。

5. 最难的部分：怎么保证目录册不是旧的

这是整个方案唯一的真难点，也是我要你重点看的一段。

md 是「事实」，index.db 是「抄件」。抄件什么时候该更新？文件系统不会主动通知你「有人改了」，只能靠你自己记着。三种触发方式，我的建议是三个都用一点：

触发方式怎么做管什么代价
A 写时同步必做 打标台的 PUT 接口写完 md，紧跟着一句 UPDATE questions SET ... 用户在界面上改的题 每次写多 1–2ms
B 启动校验必做 启动时拿 file_stamp 表（路径+mtime+大小）跟磁盘比一遍，不一致的重新灌 停机期间被别人手改的、被脚本改的 一次 1–2 秒（10 万题），只在启动时
C 低频巡检建议 后台每 10 分钟跑一次 B，或提供 build_index.py --check 手动跑 绕过 API 直接改文件（比如我重传题包） 一次 1–2 秒的 IO，可忽略
D 每请求比对不做 每次请求都 stat 全库 — 又回到「每次翻一遍书架」，白折腾
写操作的顺序有讲究，不能反 先写 md，再更新索引。顺序反了会出现「索引里有、文件里没有」——用户点进去 404。而「文件是新的、索引还是旧的」只是列表页数字慢一拍，下一分钟巡检就修正了。永远让抄件落后于原件，不能让抄件超前。

另外 10-17 定过一条纪律叫「二期只加读路径，不改写入路径」，这里的准确表述应该是：写入逻辑一个字不改，只在函数末尾加一句「索引失效」。定这条纪律的本意是防止改动打架，不是禁止一行 UPDATE。

6. 高频写入：切题、批量上传，扛得住吗

你问的这两个场景，恰好是这套设计最不担心的地方。原因一句话：图片根本不经过数据库。index.db 里只有字符串——路径、标签、状态，一张图都没有。

6.1 切一卷到底发生了多少事

Edexcel 切题（含答题册 *a 卷生成 answer_regions）时，一卷实际产生：约 90 个子题 md、90 张小问图、1 版 cut.json，外加若干 qNN.md 被原地改写。

动作实测耗时（本机）说明
Pillow 裁一小问 + WebP 编码 ×905.7 s
63.7ms/张		纯 CPU，这才是切题的真瓶颈
写 90 个子题 md105 ms小文件 IO
写索引 90 行约 2 ms实测 0.02ms/行
切一卷 6 秒，数据库只花 2 毫秒 —— 占 0.03% 加了索引之后，切题速度不会有任何可感知的变化。切的快慢只取决于 Pillow 编码速度。
但有个真风险，不是数据库 —— 是内存 切图进程（Pillow 打开 PDF 页面再裁）可能吃几百 MB。服务器总共 3.7G，而 qbank.service 设了 MemoryMax 1200M。如果切割进程和服务同时吃内存，内核的 OOM killer 会挑服务下手（因为服务有明确上限）。
→ 切割保持串行、一次一卷（现在的 batch_run.py 就是串行，别改成并发）。这不是沿用现状，是必须守住。

6.2 「换图」对索引完全透明

换一张题图 = 只改 assets/qNN.webp，md 里那行 image: assets/qNN.webp 一个字不变 → 索引里存的路径也没变 → 索引不需要任何更新。

反过来的坑要记住：换了图，nginx 的 /files/ 不能设长缓存，否则浏览器还显示旧的（10-17 踩过，已改 no-cache）。换图这件事对数据库和索引都是零成本，真正需要操心的是浏览器缓存这一层。

6.3 某局某科批量上传 100 卷

100 卷 ≈ 9000 张图（约 700MB）+ 9000 个 md（约 13MB）。走 scp/tar 直接丢目录：

项目量对数据库的影响
图片字节700 MB0 行，完全不经过 SQLite
子题元数据9000 行实测单事务 190 ms
真正瓶颈磁盘 + 网络700MB 在 100MB/s 的盘上要 7 秒；网络看上行带宽

实测「一边写 300 张 80KB 图、一边读索引」：读延迟 0.53ms（空闲时 0.044ms）。也就是说图片狂写的时候，查索引还是亚毫秒级。两者争的是磁盘带宽，不是数据库的锁。

6.4 边导入边有人打标（并发）

这是最该关心的组合：我在传 100 卷，同时 10 个老师在打标。实测三段：

场景平均P95最大结论
空闲（只读，无写）0.38 ms——基准
一边写 9000 行（60 批事务）一边读列表 237 次3.39 ms6.00 ms16.2 ms快一个量级，但仍在毫秒级
一个持有写锁 2 秒的长事务期间读0.50 ms—34.0 ms没有被阻塞
  • 读永远不等写。WAL 模式下读者看的是「事务开始前的快照」，所以有人在批量导入时，打标台不会卡住。这条是整个方案能落地的关键。
  • 但写和写会排队。SQLite 是「一写多读」，两个批量导入同时跑，后一个要等前一个提交。这是它的设计，不是 bug。
  • 平均 3.39ms 比空闲高一个量级，不是因为锁等待，而是测试里卷表从 486 涨到 1000+ 行、查询本身变大了。

6.5 三种「新数据进库」的路径，代价差 100 倍

这是实操里最要紧的一张表。同样是「有新题了」，索引怎么知道，完全取决于数据是怎么进去的：

数据怎么进来的索引怎么知道要重扫多少代价
走打标台 API 改标注写时同步（同一请求内）1 行1–2 ms
scp 传整卷（本地切好）卷目录 mtime 变了该卷 90 个文件0.13 s / 卷
原地改 qNN.md 内容
比如只补 answer_regions		目录 mtime 不变全量比 stamp10 万题 1–2 s
绕过一切直接 vim 改只能靠定时巡检全量同上，每 10 分钟一次
关键设计：失效粒度定在「卷」，不是「题」 实测 stat 1430 个卷目录 = 57ms（Windows，Linux 上约 10ms）；stat 10 万个题文件 = 1 秒以上。差 100 倍。
所以巡检只看目录：哪卷的目录时间变了，才进去细看那 90 个文件。切题、传卷这类「一次加一卷」的操作，正好落在这个粒度上，最便宜。
但别赌 mtime —— 这是最容易翻车的一点 「原地改文件内容」不会改目录 mtime（只有新增/删除/重命名文件才会）。Edexcel 切题里「给已存在的 qNN.md 补 answer_regions」正好是这种情况，卷级 mtime 检测不到。

所以我的建议：切割脚本、批量导入脚本、题包上传脚本的收尾，固定加一句
python scripts/build_index.py --paper <卷名>
单卷 0.13 秒，跑完立刻一致。这比任何自动检测都可靠，而且便宜到不值得省。

6.6 批量写入的两条纪律

  1. 小批提交，别用一个事务包 9000 行。实测：500 行逐条 commit = 133ms，5000 行单事务 = 107ms（每行差 13 倍）。但一个事务跑 3 秒会挡住其他写。→ 每 200–500 行提交一次，既能享受批量速度，又不长时间占锁。
  2. 只让服务进程写 index.db。切割脚本跑完不要自己开 SQLite 写——两个写者会让「谁在什么时候改的」彻底混乱，出问题无法定位。→ 走 --paper 参数由脚本调用，或调一次刷新接口。

本节实测（本机 Windows，2026-10-18）：Pillow 裁图+WebP 编码 63.7ms/张（1450×402 源图）；写 90 个 md 105ms；索引写 0.02ms/行；stat 486 个卷目录 19.4ms；单卷 listdir+stat 0.55ms；WAL 峰值 4.4MB。脚本：cloud/.tmp/index_stress2.py。Windows 的文件操作通常比 Linux 慢，服务器上的数字只会更好。

7. 对「数据」的影响

不会变的零影响

  • md 文件格式：front-matter 一个字段不加
  • 切割坐标、题图、layout.json：完全不碰
  • 目录结构、命名规范：不变
  • Git 里的内容：不变（index.db 进 .gitignore）
  • 前端拿到的 JSON 结构：字段一个不改

会新增的要盯住

  • 多了一份可能过期的副本——这是新增的风险，靠上面 A/B/C 三层兜住
  • 备份边界要划清：index.db 不进备份（详见第 10 节）
  • 恢复流程多一步：从备份恢复完必须重建索引，否则显示的是恢复前的状态
  • schema 版本号：表结构一改就整库重建，不写迁移脚本（重建只要 30 秒）
绝对不能做的事 不要往 index.db 里存「重新生成不出来的东西」。比如确认状态（confirmed.json）、标黄标记（flagged.json）、谁在什么时候改了什么（审计日志）。这些东西一旦进了索引库，下次重建索引就等于亲手抹掉人工成果。
这条 10-14 的讨论里已经踩到过边：「能随时重建」和「能承载写入」是互斥的。index.db 一旦开始存真数据，它就不再是索引了。

并发与进程的硬约束（这条别忘）

  • 还是单进程。"有了数据库"很容易让人想「那上多 worker 吧」——不行。SQLite 允许多进程，但你的服务里还有进程内缓存和 RLock，多 worker 会各算各的、互相看不见对方的改动。要上多 worker 得先把缓存和锁全部移出去，那是三期的事。
  • 开 WAL 模式：读写不互相堵。代价是磁盘上多出 index.db-wal 文件，定期自动合并。
  • SQLite 文件必须放本机磁盘。放 NFS / 网络盘 / 共享目录，锁机制不可靠，早晚写坏。这一条 10-14 已经记过。
  • 写操作加 5 秒忙等超时（busy_timeout=5000），避免偶发「database is locked」直接报错给用户。

9. 对「前端」的影响

前端零改动 /api/papers、/api/papers/{id}/questions、/api/questions/{qid} 的返回结构一个字段都不变。React 那边不用动一行代码，连 build 都不用重跑。

唯一的行为变化是「数据新鲜的时机」：改完一题 → 后端写完 md 顺手更新索引 → 前端刷新立刻看到新数字。仍然是即时的，感觉不出差别。

顺带能做、但现在不急着做的事

  • 服务端筛选：/api/papers?board=aqa&subject=physics&status=none。现在前端是全量拉下来自己筛，1430 卷时数据量约 300KB，还能扛，但筛选逻辑在前端会越来越重。
  • 按标签查题：有了 questions 表的 tags 列，可以做到「点一个标签，列出全库用过这个标签的题」。这个功能现在完全做不到（要现场翻 9176 个文件）。
  • 分页：卷列表 1430 条其实不需要分页，先不做。

这些都不是本次必做项。先上索引，功能以后再说——别为了「用上索引」去改前端。

11. 什么时候动手：别看「10 万题」这个数

「10 万题」是个好记的整数，但它不是合适的触发条件。按症状触发，不按题数触发。

指标当前建议触发线怎么测
启动预热耗时13.1 s> 60 s看日志里 [warmup] 预热完成 那一行
列表页 P95 响应几十 ms> 1000 ms浏览器 F12 → Network，连点 10 次看
服务进程内存 RSS约 120 MB> 600 MBsystemctl status qbank 里的 Memory 行
题文件总数9 176> 20 000find data -name "q*.md" | wc -l
我的判断 改造量是固定的（约 400 行，不会因为题多就变多）。所以做的时机应该选「没压力的时候」，不是「出事的时候」。建议在 2 万题左右、8 个学科开始铺量的那个节点做——那时候你有余量慢慢验收、对比、回滚；等到 10 万题列表页卡成 3 秒，你是在救火，还得一边救火一边改存储层。

另外提醒一句：按现在 486 卷 / 9176 题（平均 19 个文件/卷）的速度，10 万题大约是 1400–2000 卷（8 学科全量 + 小问切分）。这不远了，但要几个月。

随 Step 1 完成		 原计划四处写 md 的函数各加失效。实际实现更省：统一放在 _atomic_write() 里标记该卷 stale（一处覆盖全部写路径），cleanup_subs 单独补一处。 改一题 → 刷新列表数字立刻变（已验）；重启后仍然对 git revert（索引变旧，但 --check/重建修得回来）
Step 3
自愈兜底
已完成 10-18		 启动 stamp 校验 + --check 手动巡检 + 恢复脚本里加一行重建。 拿一份测试卷，绕过 API 直接改一个 md → 跑 check → 索引修正 —
Step 3 实际实现（比原计划更省）
原计划是「启动时全量 stamp 校验」，实际做成随目录扫描顺带对账（默认每 5 秒一次，只比 stat，几毫秒）： papers 表新增 dir_mtime，扫描时比对三件事——
① 目录 mtime 变了 → 标 stale，下次读只重灌这一卷（题包重传/切、增删子题文件都走这条）；
② 磁盘上没了的卷 → drop_paper() 删掉（不再有幽灵卷）；
③ 磁盘上有、索引里没有的新卷 → 读到时自动重建（无需人工）。
另加 build_index.py --verify（0.1 秒快速对账）与 schema 版本不符时**自动删库重建**； 全量重建期间 is_building() 为真，读路径回退文件扫描，避免与服务抢写锁。
实测：造一个假卷 → 5 秒内自动入索引（410→411）；删掉 → 5 秒内自动消失（411→410）； 卷内加一个 q02.md → 目录 mtime 变 → 下次请求该卷题数从 1 变 2。
仍然覆盖不到的：原地改已有 md 的 tags/difficulty（目录 mtime 不变）→ 靠脚本收尾 --paper 或 --check。 但这只发生在「绕过 API 直接改文件」，本来就不是常规路径。

顺序不能乱：先证明「抄出来的和原件一致」（Step 0/1），再让抄件开始跟着变（Step 2），最后才上自动纠错（Step 3）。反过来做，出了问题你分不清是抄错还是同步错。

13. 已知的坑（都是要踩的，提前写好）

#坑表征与对策
1mtime 不可信rsync / 备份恢复 / git checkout 都会刷新 mtime。→ 用（mtime + 文件大小）双字段判断，写时同步完全不依赖 mtime。
2SQLite 放网络盘写坏锁不可靠，会静默损坏。→ 只放本机 ext4。
3WAL 文件被漏掉index.db-wal 可能比主库还大。备份/复制时要么带上，要么先 checkpoint 再操作。
4双写顺序反了先 db 后 md → 用户点进去 404。→ 永远 md 优先。
5恢复后忘了重建从备份恢复 data/ 后，index.db 还是恢复前的旧状态。→ 写进恢复脚本，别靠记性。
6想趁机上多 worker进程内缓存和锁没移出去，多 worker 会互相看不见改动。→ 三期再说。
7改表结构想写迁移不值得。→ 版本号不符就整库重建（30 秒）。
8往索引里存真数据确认状态、标黄、审计日志都不许进。→ 一进就失去「可重建」这个护身符。
9把 index.db 传进 Git84MB 二进制，diff 无意义。→ 加 .gitignore，和现在 /data/* 一个道理。
10目录 mtime 只认「增删改名」原地改文件内容（补 answer_regions）不会改目录时间。→ 别赌自动检测，脚本收尾显式跑 --paper（见 6.5）。
11切图把自己撑爆Pillow 进程吃内存 + 服务 1200M 上限 → 被 OOM 杀的是服务。→ 切割串行，别并发跑多卷。

方案能做到什么代价结论

C index.db
（本方案）		 查询 0.005–3ms；内存 270MB → 50MB；启动 143s → 35s 约 400 行代码 + 一条同步纪律；多一份要维护的副本 推荐
D 全搬 PostgreSQL 多人并发最强，事务最正规 要装服务、要运维、要备份；失去 Git diff 和手改能力；2557 行读写点全要重写 三期再议
E 所有题塞一个 JSON 实现最简单 10 万题一个 140MB 文件；改一个字要重写整个文件；内存照样吃满 不做
F 内存映射（mmap） 理论上最快 Python 上很难用好；数据格式要重设计；调试困难 不做
为什么是 SQLite 而不是「自己写个索引文件」 你要的功能其实就三件：按题号取一条、按卷取一组、按条件筛一批。自己写就要处理「文件格式、并发读写、崩溃后不损坏、按范围查」——SQLite 这四件事都替你做了，而且整个库就是一个文件，删了就是删了。它是这个规模（10 万行、10 个用户）最合适的工具，不多不少。

15. 需要你拍板的四件事

1. 触发线定在哪？ 我的建议是「2 万题 / 列表 P95 > 1s / 启动 > 60s，哪个先到算哪个」。你也可以说「不管多少题，先把 Step 0 原型做出来看看」——原型不动线上代码，产物随时可扔，成本很低。
2. 现在要不要先做 Step 0？ 我倾向做。理由：① 只加一个脚本，零风险；② 能拿到你这台机器上真实的「现状 vs 索引」耗时对比，而不是我这份外推；③ 顺便把「现有 API 数字 vs 索引数字」逐项核对一遍，等于给数据做了一次体检。
3. index.db 放哪？ 建议 /opt/qbank/var/index.db（data/ 外面）。另一个选项是 data/_index/index.db，好处是「数据都在一起」直观，坏处是必须改 backup.sh 加排除规则，忘了就每天多 84MB。
4. 要不要顺手把 confirmed / flagged 也搬进 db？ 现在这两个是单个 JSON 文件，10 万题时会涨到 8–10MB，每个请求解析 300–400ms——这会变成比列表页更明显的卡顿。搬进 db 能降到微秒级，但它们是「事实」不是「派生」，不能重建。
折中做法：文件仍是事实源，db 里存一份只读副本，写文件时同步更新副本，启动时校验。这样既保住可手改，又不吃那个 300ms。
2026-10-18 补充：已单独出方案 plans/确认与标记存储方案-20261018.md，结论修正为——直接以独立的 state.db 为事实源（不要混进 index.db，否则重建索引会抹掉人工成果），同时把 flags 的指纹校验移出请求路径。要不要一起做，你定。

本机实测数据（2026-10-18）：9176 个 md / 486 卷（aqa 146、cie 210、edexcel 130）/ 8363 主题 + 813 子题 / 已打标 1265 个文件（13.8%）。
