# 确认状态 / 有误标记：存储形态改造方案

> 2026-10-18 · 对象：`data/_review/confirmed.json`、`data/_review/flagged.json`
> 结论：**换成独立的 SQLite 库 `state.db`，并把 flags 的指纹校验移出请求路径**。两件事必须分开做。

---

## 0. 先分清两件事（这是本方案的核心）

现在 `confirmed.json` 慢，大家容易归因到「文件太大」。其实有两个独立的问题，混在一起会治错：

| # | 问题 | 表现 | 治法 |
|---|---|---|---|
| ① | **存储形态**：单个大 JSON，每次写都要全量重写 | 确认一次 = 深拷贝 + 序列化 11MB + 写盘，**约 180ms** | 换成 SQLite 表（写一行 0.02ms） |
| ② | **校验时机**：`flags.prune()` 在**每个读请求**里跑 | 每条标记都要 `find_question` + 2 次 `stat` | 移出请求路径（低频/按需） |

**只做 ① 不做 ②**：JSON 换成了 SQLite，但 `/api/papers` 每次还在做 N 次 stat，该慢还是慢。
**只做 ② 不做 ①**：列表页快了，但每确认一次仍要重写 11MB 文件，而且多人并发照样丢更新。

所以两个都要做，且 ② 的收益更直接（在请求路径上）。

---

## 1. 现状实测成本（10 万题规模）

### confirmed.json

| 操作 | 实测 | 说明 |
|---|---|---|
| 文件体积（10 万条） | **11.3 MB** | 每条 `"qid": {"at": "...", "by": null}` |
| 写一次（深拷贝 + 序列化 + 写盘） | **约 180 ms** | 深拷贝 110ms + 序列化 52ms + 写盘 |
| 读一次（缓存失效后重新解析） | **64 ms** | 每次写完缓存就失效 → 下一个请求吃这 64ms |
| 内存里存一份 set | 约 10 MB | `confirmed_ids()` 返回的 set |

**关键**：`set_confirmed()` 是「读-改-写」——`load()` 整份读进来，深拷贝，改一个键，再整份写回。
10 个人同时确认不同题，后写的会把先写的覆盖掉。**这是正确性问题，不只是性能问题。**

### flagged.json

| 操作 | 实测 / 估算 | 说明 |
|---|---|---|
| 文件体积 | 每条约 400 字节（含 sha256） | flag 率 2% → 2000 条 ≈ 800KB，**体积不是问题** |
| `prune()` 每请求成本 | 2000 条 × (1 次 `find_question` + 2 次 `stat`) | 约 **40–100 ms / 每个列表请求** |
| prune 有变更时 | 还会顺手**写盘** | 读请求里发生写，最不该出现的事 |

**关键**：`flags.flagged_ids()` → `prune()` → 遍历所有标记逐条校验文件指纹。这意味着**每个打开列表页的人，都在替全库做一遍指纹校验**。标记越多越慢。

### 换成 SQLite 之后

| 操作 | 实测 |
|---|---|
| 单条确认写入（含 commit） | **0.02 ms**（对比 180ms，快约 9000 倍） |
| 全量读 10 万 id 到 set | **38.7 ms**（只在启动做一次） |
| 按 id 查一条 | 0.0035 ms |
| 灌 10 万条（一次性迁移） | 173 ms |
| 库体积 | **14.1 MB**（比 JSON 的 11.3MB 略大，见 §5） |

## 2. 推荐方案

### 2.1 新建独立库 `state.db`，**不要塞进 index.db**

```
/opt/qbank/var/
  ├── index.db    ← 从 md 抄出来的索引，100% 可重建，丢了重跑，不进备份
  └── state.db    ← 确认状态 + 有误标记，不可重建，必须进备份
```

**为什么必须分开**：`index.db` 的护身符是「随时可删可重建」。一旦把确认状态混进同一个库，重建索引就等于抹掉人工成果——这正是 10-14 定过的红线。两个文件，两种纪律，一眼分得清。

### 2.2 表结构

```sql
CREATE TABLE confirms (
  unit_id  TEXT PRIMARY KEY,   -- 确认单元：整题=主题 qid；切分题=小问 qid
  at       TEXT NOT NULL,      -- ISO 时间
  by_user  TEXT                -- 谁确认的（现在这个字段恒为 null，见 §6）
);

CREATE TABLE flags (
  qid      TEXT PRIMARY KEY,
  at       TEXT NOT NULL,
  by_user  TEXT,
  note     TEXT,
  fp       TEXT NOT NULL,      -- 指纹 JSON：mt/sz/sha/imt/isz
  fp_ok_at TEXT                -- 上次指纹校验通过的时间（用于错峰巡检）
);

CREATE INDEX idx_flags_ok ON flags(fp_ok_at);
```

时间字段想省空间可以改 `INTEGER`（unix 秒），10 万行能省 3–4MB。**但建议先别省**，`TEXT` 直接可读，排查问题时省事。

### 2.3 读写路径怎么变

| 场景 | 现在 | 改后 |
|---|---|---|
| 打开列表页 | 解析 confirmed、跑 prune 校验 N 条 | 内存里的两个 set，**0 成本** |
| 确认一题 | 深拷贝 + 重写 11MB，180ms | 一条 UPSERT，0.02ms + 更新内存 set |
| 取消确认 | 同上 | 一条 DELETE |
| 打开某题详情 | 已确认状态从 set 查 | 同 |
| 标「有误」 | 重写整个 flagged.json | 一条 UPSERT（带上指纹） |
| 判断是否 flagged | prune 全量校验 | 查内存 set |
| 指纹失效检测 | 每个列表请求都做 | **见 2.4** |

### 2.4 指纹校验搬到哪（这是 ② 的解法）

现状是「每个读请求都校验一遍」。改成三处，按优先级：

1. **打开单题详情时校验那一条**（`GET /questions/{qid}`）——用户真正要看这题时才验，精准、零浪费。验到失效就把记录删掉，返回「未标记」。
2. **后台低频巡检**：每 5–10 分钟，只校验 `fp_ok_at` 最久远的 200 条，轮转覆盖全库。10 万题里 2000 条标记，一轮 10 次巡检走完。
3. **题包重传后主动校验**：`reupload` 脚本收尾调一次 `flags.recheck(qid)`，一步到位。

**列表页从此完全不碰文件系统。**

## 3. 三个方案对比

| | A 保持现状 | B JSONL 追加日志 | **C SQLite `state.db`（推荐）** |
|---|---|---|---|
| 写一次确认 | 180 ms，重写 11MB | ~0.05 ms（append 一行） | **0.02 ms** |
| 并发丢更新 | **有**（读-改-写） | 无（append 不冲突） | 无（事务 + 主键） |
| 启动加载 | 64 ms | 重放 10 万行，约 200 ms | **38.7 ms** |
| 文件可读可手改 | 是 | 是 | **否**（二进制） |
| 审计查询 | 要靠代码遍历 | 靠自己扫行 | **一条 SQL** |
| 需要额外维护 | 无 | compaction 逻辑（半行/重复行/乱序） | 备份前要 checkpoint |
| 技术栈 | — | 新 | **与 index.db 统一** |

**为什么选 C 而不是 B**：JSONL 看起来更「轻」，但没有约束——重复行、半行、乱序都得自己处理，还要写 compaction。SQLite 把这些全包了，而且 `index.db` 本来就要上 SQLite，运维上只多一个概念，不多一套技术。

**什么时候反而该选 B**：如果你非常在意「用记事本打开能看懂、能手改」。但说实话，这两个文件本来就不该手改——手改一个 qid 打错字，界面上就多出一条永远对不上的确认记录。

## 4. 迁移步骤（每步可单独回滚）

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 写 `scripts/migrate_state.py`：读两个 JSON → 灌 `state.db` → **比条数**（JSON 里几条 = 表里几行，不等就中止） | 打印 `confirmed: 1234 → 1234`、`flags: 12 → 12` |
| 2 | 旧文件改名为 `confirmed.json.migrated-20261018`、`flagged.json.migrated-20261018`（**不删**，留一周） | 目录里两个 `.migrated` 文件 |
| 3 | 改 `review.py` / `flags.py`：底层换成 SQLite，**对外函数签名一个都不变**（`is_confirmed` / `set_confirmed` / `confirmed_ids` / `get` / `set_flag` / `flagged_ids`） | `api.py` 和前端**零改动** |
| 4 | 拆 prune：请求路径移除，改成「详情页校验 + 低频巡检」 | 列表页响应时间对比；故意改一个 md 再打开详情，标记应消失 |
| 5 | `backup.sh` 加 state.db（见 §5） | 手动跑一次备份，解包能看到 state.db |

**函数签名不变**是这条改造最舒服的地方：`api.py` 一处不用改，前端完全无感。

## 5. 三个必须注意的点

### 5.1 备份不能直接 rsync 一个正在写的 SQLite

`backup.sh` 是 `rsync --link-dest`。**正在写的 WAL 库直接 rsync 会拿到不一致的快照**（主库 + WAL 分离）。两种正确做法：

```bash
# 做法一：先 checkpoint 再 rsync（简单）
sqlite3 /opt/qbank/var/state.db "PRAGMA wal_checkpoint(TRUNCATE)"
rsync -a /opt/qbank/var/state.db /备份路径/

# 做法二：用 SQLite 自己的原子快照（更稳，推荐）
sqlite3 /opt/qbank/var/state.db "VACUUM INTO '/备份路径/state.db'"
```

**恢复时**：state.db 回来了，服务要重启（或调一次 reload），否则内存里的 set 还是旧的。

### 5.2 空间略增：14.1MB vs 11.3MB

SQLite 有 B 树索引和页对齐开销，10 万条要 14MB，比 JSON 大 3MB。**这不是优势，但也不是问题**——相对题库 9.9G 是 0.14%。想省可以换 INTEGER 时间戳，能压到 10MB 左右。

### 5.3 不能用编辑器改了

以后要排查「这题到底确认没」，用：

```bash
sqlite3 /opt/qbank/var/state.db "SELECT * FROM confirms WHERE unit_id LIKE '%ph01-q01%';"
```

或者给它配一个 `state_dump.py`，随时导出成和现在一样的 JSON 格式（只读、给人看）。

## 6. 顺带补一个现存缺陷

`api.py` 第 410 行：`review.set_confirmed(qid, payload.confirmed)` —— **没传操作人**。所以 `confirmed.json` 里 `by` 永远 `null`。而 `flags` 那边是传了 `by_user` 的。

十人打标时这会很难查：出错了不知道谁确认的。改表结构时顺手补上——接口里 `ident` 已经有了，加个参数就行。补完之后能直接查：

```sql
SELECT by_user, COUNT(*) FROM confirms GROUP BY by_user ORDER BY 2 DESC;
```

「谁打了多少题」这种统计，现在只能翻审计日志拼，改完是一句话。

---

## 7. 什么时候做

**建议独立做，而且可以比 index.db 早。**

理由：
- 改动面小：两个模块、约 200 行、**对外签名不变**，前端零改动
- 它解决的是**正确性问题**（并发丢更新）+ 请求路径上的浪费，跟题量无关，现在做就有收益
- 和 index.db 没有依赖关系：一个存「抄件」，一个存「事实」，两个文件互不影响

**唯一的前置条件**：确认现在打标台上没人正在批量干活（迁移那 30 秒要停服务）。
