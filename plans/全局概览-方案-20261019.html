02判定逻辑（唯一实现，别写第二套）

判据直接复用 api.list_papers() 里那段循环（api.py:214-235），抽成一个公共函数，列表页和概览页都调它。这是整份方案最重要的一条约束：不允许为概览页另写一套判定，否则两个页面迟早对不上。

# api.py 新增，替换 list_papers 内联循环
def paper_progress(p, conf: set[str], flagged: set[str]) -> dict:
    qs = p.questions()
    verified = 0
    flagged_n = 0
    tagged_any = False
    for q in qs:
        units = _units_of(q["qid"], q.get("split"), q.get("sub_ids") or [])
        if q.get("any_tagged"):
            tagged_any = True
        hit = str(q["qid"]) in flagged or any(u in flagged for u in units)
        if hit:
            flagged_n += 1
        elif _verify_state(units, conf)[0] == "all":
            verified += 1
    active = max(0, len(qs) - flagged_n)
    if active > 0 and verified >= active:
        state = "all"
    elif tagged_any or verified:
        state = "some"
    else:
        state = "none"
    return {"state": state, "verified": verified, "flagged": flagged_n}
三个边界，实现时别漏

① 整卷全被标「有误」：active = 0，判不了「通过」，落到淡绿（因为标有误前它必然打过标）。不要判成深绿。

② 切了但没生成任何子题：units 为空，_verify_state 返回 none，既不通过也不算已核对，符合预期。

③ 0 道题的卷（切坏了）：直接判灰，不要除零。

03后端接口

路由
GET /api/overview（api.py，与 /api/papers 同层）
权限
ident = auth.current(request)；非 admin 一律 403。不做学科过滤——概览的意义就是全局。
返回
{"papers": [...], "summary": {...}, "generated_at": "..."}
每卷字段
id, board, qualification, subject, paper_code, year, session, state

只要 8 个字段，不返回题目明细、不返回 tags、不返回分数。

取数：一条 SQL，判定仍在 Python

-- index_db 里一次拉全量最小列集（10 万行约 60–80ms）
SELECT q.paper_id, q.qid, q.parent_qid, q.split, q.tags
FROM questions q ORDER BY q.paper_id

-- 卷级元数据仍读 papers 表（标题/年份/考试局）
SELECT paper_id, board, qualification, subject, paper_code, year, session FROM papers

确认集合用 review.confirmed_ids()、有误集合用 flags.flagged_ids()（都已是内存 set，零 IO）。

为什么不让 SQL 直接算到卷级

索引里切分题的主行和子题行都在表里（主行 split=1, parent_qid IS NULL），要正确聚合必须排除主行、再按「主题题」把子题归组、再处理 flagged 的向上传染。纯 SQL 能写但会变成一个 40 行的嵌套 CTE，一旦理解错就与打钩逻辑漂移。SQL 只负责搬数据，判定复用 Python 那段现成代码——多花 60ms，换「永远不会对不上」，值。

缓存

60 秒进程内缓存，键为 (index_db.generation(), state.rev())。任何写操作（保存标注 / 确认 / 标有误 / 切卷）都会改变其中一个值，缓存自动失效，不需要手工清理。

  • state.py 加一个 _rev 整数，set_confirmed / set_flag / delete_flag 里 +1，暴露 state.rev()（约 6 行）。
  • 缓存未过期直接返回，命中 < 5ms；冷启动一次约 150ms。

05性能与容量

合成数据实测（7500 卷 / 10 万单元，SQLite 结构照抄 index.db，Windows 本机；云端 Linux 约再快 4 成）：

环节耗时说明
现状式：逐卷 questions() 构造 10 万个 dict337 ms概览页不能走这条
一条 SQL 拉最小列 + Python 聚合≈ 150 ms本方案采用的冷路径
缓存命中< 5 ms60s 内的绝大多数请求
JSON 1.3 MB → gzip23 KB传输可忽略
前端 7500 格构建 + 布局6.4 + 12.5 ms3 万格也才 52ms，不需要 canvas

结论

10 万题（≈7500 卷）时概览页本身完全不是瓶颈：格子数按卷算、不按题算；后端冷 150ms、热 5ms；前端 20ms。真正该提前修的是 _SCAN_TTL。

06实施顺序

  1. P0 · 与概览一起做必须：抽 paper_progress() → 改 list_papers 复用它（回归验证列表对钩不变）→ 新增 /api/overview + 缓存 → 前端按钮与页面。
  2. P1 · 顺手做建议：_SCAN_TTL 5s → 60s；上传卷的接口里显式调一次 store.invalidate_scan()。当前 1250 卷实测 110ms，还不痛，但这是唯一会随卷数线性变慢的全局开销。
  3. P2 · 卷数破 2 万再说暂不做：把三个计数物化进 papers 表（读 8.7ms）；前端换 canvas。四个写入口都要维护物化列，一致性风险大于收益。

验收

  • 概览里深绿的卷数 = 左侧卷列表带 ✓ 的卷数，逐卷人工抽查 10 卷一致。
  • 在打标台确认一题后回概览，60 秒内颜色变化（缓存键生效）。
  • 非 admin 直接请求 /api/overview 返回 403。
  • 点击任意格子能跳到对应卷，且三个下拉都被同步。

07明确不做

  • flagged 的红点 / 红框 —— 你说了不用，颜色只表达进度。
  • 自动刷新、实时推送 —— 60 秒陈旧度足够。
  • 学科维度权限（lead 只看本科）—— 当前只给 admin；以后要开，加个 subject 过滤参数即可。
  • 导出一张图 / 分享链接 —— 需要再说。
