题库打标平台 · 云部署方案

腾讯云轻量 · 6 学科 · 73 个账号 · 9.6 万题
编写 2026-10-17 目标机 140.143.229.85（Ubuntu 24.04 / 2 核 / 3.6G / 59G） 状态 待评审，未执行
  1. 服务器现有配置够跑一期，但 10 万题必须加一层索引。 现在的代码每个请求都要扫全库目录、每卷都要读全部题的元数据；到 10 万题时「打开题库列表」这一个动作会从几十毫秒涨到十几秒——这跟多少人同时用无关，一个人也会卡成这样。
  2. 73 个账号不需要多进程。 峰值并发按 10 人算，约 0.5 QPS，单进程绰绰有余。多开 worker 反而会破坏现有进程内缓存和确认记录锁。单进程 + nginx 缓存是正解。
  3. 磁盘先不扩，够用但不宽裕。 6 科合计约 9.6 万题、9.0 GB（PDF 不传），加一份全量备份 18.0 GB；机器已用 20 GB，59 GB 盘放完剩 21 GB。到 85% 占用（约剩 9 GB）就必须做决定：扩盘或把备份挪到对象存储。

3性能：9.6 万题的三个坎

这三处是实测代码路径，不是推测。它们决定「要不要加索引层」。

代码路径现在（8619 md）9.6 万题时必须做的改动

每个请求都跑		 遍历 4 层目录 + 439 次 glob

组合起来看：「打开题库列表」这一个动作 = _scan_papers + 每卷 summary()， 在 9.6 万题时是十几秒。哪怕只有 10 个人同时点一下，这台 2 核机器也要排队。这不是加内存能解决的，必须把「全库扫描」从请求路径里拿掉。

结论：加一层 SQLite 索引（index.db），不改现有文件结构。 md 文件仍是唯一事实源，索引只是可随时重建的读缓存。这是项目里早就记过的三层架构： 文件（事实）→ index.db（可重建）→ 运行期缓存。改造约 300–400 行，不动数据本身。

4架构分期

不做一次性大改，按题库规模触发。每期的前提都是上一期已稳定运行。

期触发条件做什么改动量
一期
现在		 题库 ≤ 2 万题
≤ 30 个账号		 搬服务器 + 登录认证 + systemd + nginx + 备份。业务代码只改监听地址 约 150 行（认证中间件 + 账号生成）
二期
2–10 万题		 列表接口响应 > 1 秒
或题库 > 2 万题		 加 index.db：questions / papers 两张表 + 写入同步 + 启动后台构建 约 350 行（新增 index.py + 改 4 个调用点）
三期
> 10 万题		 单进程 CPU 打满
或多学科要独立部署		 才考虑多进程 / 拆服务 / 换 PostgreSQL。此时缓存和锁必须外置 另议
为什么二期不是「多开几个 worker」： 现有 store._lock、_meta_cache、review._cache 全是进程内状态。开两个 worker，A 改的题 B 看不到，两个进程同时写 confirmed.json 会互相覆盖。 要并行必须先让状态离开进程——那正好就是 index.db 要做的事。所以顺序不能反。

四种角色

角色权限适用
admin全部学科、词表增改、账号管理、确认记录管理你（2 个）

实现方式

  • 账号存 /opt/qbank/users.yaml，密码只存 pbkdf2_hmac 哈希，不存明文
  • 登录成功后签发 HMAC 签名 cookie（无状态，不引入 session 表），有效期 12 小时
  • 中间件统一校验 /api/* 和 /files/*。静态路径必须一起护住，否则知道 URL 就能直接下载整库
  • 批量生成 92 个账号 + 随机初始密码，导出 CSV 分发；CSV 生成后提醒删除
  • 首次登录强制改密；管理员可一键重置
已定：B 严格隔离。 账号绑定学科，跨学科一律不可见也不可写。
落地三个检查点：① /papers 只返回本人学科；② GET /questions/{qid} 校验 qid 归属，跨科返回 404（不是 403，避免泄露存在性）； ③ 写接口（annotation / confirm / split / taxonomy）再校验一次学科与角色。admin 是唯一例外。
并发按峰值 10 人算。 73 个账号是「备着」，不是「同时用」。这个数字把带宽和 CPU 压力直接打到可以忽略的量级—— 每人 20 秒翻一题，峰值约 0.5 QPS、0.5 Mbps。
但要注意：规模问题与并发无关。它是「单次请求要扫 9.6 万个文件」，哪怕只有 1 个人用，列表页照样要十几秒。 所以二期的索引层不能因为「人少」就省掉。

6AI 打标通道（保留并上云）

现在 AI 打标是直接对本机 http://127.0.0.1:8642/api/… 裸调，没有认证。 上云后所有接口都要凭证，AI 也一样——但接口契约不用改，只改 base_url 和加一个请求头。

三种接入方式

方式做法评价
A. API Key 建一个 service 角色的账号，签发长期 token，AI 用 Authorization: Bearer 调 推荐 与人工账号同一套权限与审计，可单独吊销
B. 服务器内 localhost 把 AI 脚本放到服务器上跑，走 127.0.0.1 免认证 次选 要占服务器 CPU/内存，且模型调用还得回传
C. SSH 直接改 md 绕开接口，直接写文件 禁止 会绕过 primary_tag 校验、确认失效、索引更新

账号模型

users.yaml 里多一种角色，AI 用独立身份，写进库里的 by 字段能和人工区分开：

users:
  - username: ai-tagger
    name: AI 打标
    role: service
    subjects: ["*"]          # service 例外：可跨学科
    key_hash: pbkdf2_sha256$260000$...$...

Key 只在创建时明文显示一次，之后只存哈希。要吊销就删这一条，不影响任何人类账号。

中间件怎么认

同一个中间件，先看 Bearer 再看 cookie，两条通道汇到同一个身份对象：

auth = request.headers.get("authorization", "")
if auth.startswith("Bearer "):
    ident = verify_api_key(auth[7:])        # service 账号
else:
    ident = verify_cookie(request.cookies.get("qb_session"))  # 浏览器
request.state.user = ident

AI 侧要改的只有两行

现有 ai-tagging 技能的调用序列完全不变，只是请求模板换成：

BASE = "http://140.143.229.85"
HEAD = {"Authorization": "Bearer <token>"}

GET  {BASE}/api/papers
GET  {BASE}/api/papers/{paper_id}/questions
GET  {BASE}/api/questions/{qid}          # 拿 available_tags 与 image_url
PUT  {BASE}/api/questions/{qid}/annotation   # 提交 tags / primary_tag
为什么这个接口够用： PUT /annotation 已经处理了主标签补全、多标签缺主报错、 确认记录失效、索引更新这套逻辑。AI 只要给对 tags 和 primary_tag， 其余行为与人工点击保存完全一致——不会出现「AI 写的和人工写的不一样」。

读图走哪边

方案代价前提
读本地 data/ 里的图零流量、最快本地与云端必须是同一份数据，否则 qid 对不上
从云端下载 /files/…约 82 KB/题，1000 题约 82 MB无，永远一致

建议：日常用本地图（快），但每次开工前先 GET /api/papers 核对卷列表， 确认要打的卷在云端存在、题号一致。出现不一致就改走云端下载。

三条运行纪律

  • 只处理 status=none。这条规矩的副作用正好是「天然幂等」——断了重跑不会覆盖已完成的部分。
  • 串行跑，一次一卷，每条请求间隔约 100 ms。1000 题约 2–5 分钟，既能压住写入频率，也不至于和人抢资源。
  • 不要和老师同时标同一卷。软锁对 service 账号默认不阻塞（否则 AI 会被自己卡住）， 所以靠约定：AI 跑哪卷，提前在群里说一声，或挑老师不在的时段跑。

审计与安全

项做法
写入留痕qNN.md 落 annotated_by: ai-tagger；审计日志记 before/after
Key 存放只在本机环境变量或技能配置里，不进 git、不进日志、不写进报告

二期再考虑、现在不做： 批量接口 POST /api/annotations/batch（把 1000 次往返压成 10 次）、 AI 任务看板。一期逐题调完全够用，先别为了省 3 分钟引入一套批量事务的错误处理。

7部署步骤

每步都给了验证方法和回退动作。整体可回退到「删掉 /opt/qbank + 停服务」，不动机器上已有的 OpenClaw。

系统依赖

sudo apt-get update
sudo apt-get install -y python3.12-venv nginx rsync

为什么装 python3.12-venv：Ubuntu 24.04 自带的 python3 -m venv 会因为缺 ensurepip 直接失败，这是实测踩到的坑。

验证：nginx -v、rsync --version、python3 -m venv /tmp/t && rm -rf /tmp/t

目录骨架

sudo mkdir -p /opt/qbank/{data,backup,logs}
sudo chown -R ubuntu:ubuntu /opt/qbank
目录层级不能随意改。 store.py 和 api.py 用 parents[2] 定位 data/、schema/、scripts/，所以服务器上必须是 /opt/qbank/{data, schema, scripts, workbench/{backend, frontend/dist}} 这个形状， 不能只传 backend 目录。

上传代码

在本地项目目录执行。代码包很小（backend 80 KB + dist 317 KB）。

cd /d/Tasks/questionBank
tar cf - --exclude=__pycache__ \
  workbench/backend workbench/frontend/dist \
  scripts/render_subsplit.py scripts/render_questions.py schema \

验证：ls /opt/qbank/workbench/backend 应有 5 个 py，/opt/qbank/scripts 应有 2 个。

Python 环境

python3 -m venv /opt/qbank/venv

同步题库数据（不传 PDF，先改软校验）

传之前先改 render_subsplit.py 的三行校验，否则 Edexcel 卷切分会直接报错（见第 2 节红框）。

# 只传题图与 md/json，不传 PDF（省 1.8 GB）

  -e "ssh -i ~/.ssh/qbank_deploy" \
  ~/data/ ubuntu@140.143.229.85:/opt/qbank/data/

tar cf - --exclude='*.pdf' data | ssh -i ~/.ssh/qbank_deploy ubuntu@140.143.229.85 \
  'tar xf - -C /opt/qbank --strip-components=1'
不要用 sudo 传文件。 服务以 ubuntu 用户运行，文件一旦归 root， 打标保存时会 Permission denied。若已经传错，一条命令修正： sudo chown -R ubuntu:ubuntu /opt/qbank/data

验证：find /opt/qbank/data -name '*.webp' | wc -l 应等于 7396， find /opt/qbank/data -name '*.pdf' | wc -l 应为 0。

认证中间件

新增 backend/auth.py（约 120 行），改 main.py 挂载。要点：

  • POST /api/login：校验 users.yaml 的 pbkdf2 哈希，签发 cookie
  • 中间件白名单只放行 /api/login、/assets/*、/favicon.ico
  • 其余路径（含 /files/）一律校验 cookie，未通过返回 401
  • 把用户名注入 request.state.user，供写操作记录 by 字段
最容易漏的一处：/files/ 是 StaticFiles 直接挂载的，如果不单独覆盖， 加完登录页照样能通过直链下载全部题目和 PDF。中间件必须对静态路径同样生效。

systemd 常驻

sudo tee /etc/systemd/system/qbank.service >/dev/null <<'EOF'
[Unit]
Description=Question Bank Workbench
After=network.target

[Service]
User=ubuntu
WorkingDirectory=/opt/qbank/workbench/backend
Environment="PYTHONPATH=/opt/qbank/workbench/backend"
ExecStart=/opt/qbank/venv/bin/python -m uvicorn main:app \
  --host 127.0.0.1 --port 8642 --workers 1
Restart=always
RestartSec=3
MemoryMax=1200M

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now qbank

为什么 --workers 1：缓存与锁都是进程内的，多 worker 会导致缓存不一致和确认记录互相覆盖。 为什么 MemoryMax：OpenClaw 的 headless Chrome 会波动，限制本服务上限，避免 OOM 拖死整机。

验证：systemctl status qbank + curl -s --noproxy '*' http://127.0.0.1:8642/api/taxonomy | head -c 80

nginx 反向代理

sudo tee /etc/nginx/sites-available/qbank >/dev/null <<'EOF'
server {
    listen 80 default_server;
    server_name _;
    client_max_body_size 32m;

    location / {
        proxy_pass http://127.0.0.1:8642;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 120s;
    }

    location /files/ {
        proxy_pass http://127.0.0.1:8642;
        proxy_set_header Host $host;
        add_header Cache-Control "no-cache";
    }

    location /assets/ {
        proxy_pass http://127.0.0.1:8642;
        proxy_set_header Host $host;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }
}
EOF
sudo ln -sf /etc/nginx/sites-available/qbank /etc/nginx/sites-enabled/qbank
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
/files/ 一定不能设长缓存。 题图会被重新切割覆盖，但 URL 固定是 /files/…/q04.webp，没有版本号。一旦给 30 天或 7 天缓存，老师换图后看到的还是旧图， 刷新也不管用，只能清浏览器缓存。
用 no-cache（不是 no-store）：文件没变时后端 ETag 返回 304，几乎不耗带宽； 文件一变立刻拿到新的。/assets/ 可以长缓存，因为 Vite 给文件名带了内容哈希。
一期全部走反代、不让 nginx 直接读文件，是为了让认证只有一个入口。等二期图多了， 再改成 nginx 直服静态文件 + auth_request 回查后端，那时才有必要。

  • 确认已有 TCP:80 放通规则；没有就新增，来源 0.0.0.0/0
  • 确认 22 仍然只对必要来源开放

验证：在本地浏览器打开 http://140.143.229.85，应看到登录页而不是超时。

rsync -a --delete \
  --link-dest=/opt/qbank/backup/latest \
  /opt/qbank/data/ "$SNAP"/

# 2) 账号文件单独存一份（不在 data/ 下，不进上面的快照）
cp /opt/qbank/config/users.yaml /opt/qbank/backup/users-"$D".yaml 2>/dev/null || true

# 3) 滚动指针 + 清理 7 天前的快照与账号副本
ln -sfn "$SNAP" /opt/qbank/backup/latest
find /opt/qbank/backup -maxdepth 1 -type d -name '20*' -mtime +7 -exec rm -rf {} +
find /opt/qbank/backup -maxdepth 1 -name 'users-*.yaml' -mtime +7 -delete

echo "[$(date -Iseconds)] snapshot $SNAP ok"
EOF
sudo chmod +x /opt/qbank/backup.sh
( crontab -l 2>/dev/null; echo "0 3 * * * /opt/qbank/backup.sh >> /opt/qbank/logs/backup.log 2>&1" ) | crontab -

它在做什么（这是备份方案的核心）

rsync --link-dest 做的是硬链接快照，不是每天复制一份全量：

快照新增占用说明
第 1 天9.0 GB完整复制一份
第 2 天约 10 MB只有当天改动过的 md/json 是新文件，7000 多张图全部是指向第 1 天的硬链接，不占空间
第 3–7 天每天约 10 MB同理
7 天总计约 9.1 GB而不是 7 × 9.0 GB

硬链接的意思是：两个文件名指向磁盘上同一份数据。所以删掉某一天的快照，只要别的快照还链着这个文件，数据就还在； 这也意味着恢复任何一天，都是当天那个完整状态，不是增量拼出来的。

恢复怎么做

# 1) 先停服务，避免恢复过程中有人写入
sudo systemctl stop qbank

# 2) 把某天的快照整体覆盖回去（先确认日期目录存在）
ls /opt/qbank/backup/
sudo rsync -a --delete /opt/qbank/backup/2026-10-20/ /opt/qbank/data/

# 3) 账号文件也回滚（如果需要）
sudo cp /opt/qbank/backup/users-2026-10-20.yaml /opt/qbank/config/users.yaml

# 4) 启动服务
sudo systemctl start qbank

怎么确认备份是好的（别等出事才发现）

# 看今天的快照是不是完整：文件数应与线上一致
find /opt/qbank/data -name '*.md' | wc -l
find /opt/qbank/backup/latest -name '*.md' | wc -l

# 抽查一个文件内容是否一致（应无输出）
diff /opt/qbank/data/edexcel/a-level/physics/2024-june/q04.md \
     /opt/qbank/backup/latest/edexcel/a-level/physics/2024-june/q04.md
三个盲区，必须知道：
① 备份和原件在同一块盘——能防误删、防改错，防不了磁盘或机器故障。真要灾备，得再推到对象存储或另一台机器；
② root 权限的误操作会连备份一起删（比如 rm -rf /opt/qbank）；
③ 没有异地副本时，机器挂了就只有本地那份主副本能救。所以本地那台机器上的 data/ 不要删，它是最后一道保险。

8日常运维：上传新切的卷

要不要重启后端？—— 不用

后端每次处理请求前会扫一遍目录树的 mtime 快照（_scan_papers），和上次比对： 新增一个 session 目录、或往已有目录里加题，都会让父目录 mtime 变化，于是自动重建卷列表。 改已有 md 也不用手动干预——read_meta 按文件的 mtime + size 判断缓存是否失效。

操作是否重启实际行为
新增一整卷否下个请求自动发现
往已有卷加题否同上
覆盖重切后的 md / 图否md 走 stat 校验；图由缓存策略处理
删除某一卷否目录 mtime 变化即感知
改了后端 .py是sudo systemctl restart qbank
改了 taxonomy json否词表按文件签名热加载
唯一会「卡一下」的地方： 新题第一次被点开时，qid 索引里没有它，会触发一次全库索引重建。 现在 8619 个文件约 3 秒，之后就正常。到 10 万题时这一步会变成 30–60 秒——这正是二期要解决的事。

上传方式

整个 session 目录一起传，不要只传 webp。图和 md、layout.json 是配套的，只换图会让坐标和题号对不上。

# 假设本地已切好一卷：data/edexcel/a-level/physics/2024-june/
rsync -av -e "ssh -i ~/.ssh/qbank_deploy" \
  data/edexcel/a-level/physics/2024-june/ \
  ubuntu@140.143.229.85:/opt/qbank/data/edexcel/a-level/physics/2024-june/

一次传多卷就传上层目录：

rsync -av --exclude='*.pdf' -e "ssh -i ~/.ssh/qbank_deploy" \
  data/edexcel/a-level/physics/ \
  ubuntu@140.143.229.85:/opt/qbank/data/edexcel/a-level/physics/
三条禁忌：
① 别用 sudo 传——文件属主会变 root，服务写不进去；
② 别在传的过程中让人在网页上打这一卷的标——可能读到半截文件；
③ 别只覆盖 assets/ 里的图而不带 qNN.md 和 layout.json。

传完的验证：浏览器刷新 → 左侧卷列表出现新卷 → 点开第一题，图能显示、题号对得上。
